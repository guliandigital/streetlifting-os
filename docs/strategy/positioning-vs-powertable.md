# Positioning vs PowerTable / PowerGage

Date: 2026-04-30
Status: strategic memo. Anchors the product framing used by `docs/current-implementation-plan.md`.

## 1. Goal

Streetlifting OS должен полностью заменить PowerTable и PowerGage для организаторов соревнований по **стритлифтингу и weighted calisthenics**. Не для пауэрлифтинга — там PowerGage уже закрывает рынок, и наш домен не пересекается. Мы заменяем эти системы там, где федерация проводит ISF/WSF/НАП/FinalRep-турниры.

"Полностью заменить" означает покрыть весь job-to-be-done организатора, а не каждую техническую фичу референсов. У PowerTable есть Telegram-бот, 1C, Firebird, белые ярлыки на рабочем столе — это не цели, а формы реализации, и часть из них — технический долг, который мы намеренно не воспроизводим (см. `current-implementation-plan.md` §3.2).

## 2. Почему текущий клиент ощущается ближе к OpenLifter, чем к PowerTable

OpenLifter и наш V1 решают **одну и ту же роль**: оператор у одного ноутбука, один турнир, один файл. Полный цикл setup → registration → weigh-ins → judging → results → print реализован, но он живёт в одном клиенте и одной голове.

PowerTable и PowerGage решают **связку ролей**:

- секретарь федерации (до соревнования);
- организатор / главный судья (workflow и расписание);
- секретарь взвешивания (отдельный экран);
- оператор помоста (judging);
- судьи (отдельные пульты, иногда телефоны);
- ассистенты (экран нагрузки, порядок выхода);
- ведущий (свой экран);
- зал (табло);
- спортсмен / тренер (заказ подхода, уведомления);
- зритель (live-протокол);
- федерация (рекорды, санкции, разряды).

Разница не в красоте UI и не в количестве кнопок. Разница в том, что у PowerTable вокруг turnier state существует **N клиентов с разными правами доступа**, а у нас — **один клиент**. Это исходное архитектурное различие, не косметика.

## 3. Ключевой архитектурный реframe

### Было: "слои до / вокруг / после соревнования"

Логичная декомпозиция, но она временна́я и подталкивает строить отдельные продукты для разных моментов жизненного цикла.

### Стало: "одно соревновательное состояние, N ролевых клиентов"

| Роль | Где живёт | Что видит | Что может писать |
|---|---|---|---|
| Секретарь федерации | Layer 0 / Layer −1 admin | Заявки, оплаты, санкции, рекорды | Утвердить регламент, выпустить sanction, открыть запись |
| Организатор | Layer 1 (оператор) + Layer 0 (заявки) | Полный meet state | Setup, расписание, потоки, корректировки |
| Секретарь взвешивания | Layer 1 view "weigh-in" | Регистрация, веса, категории, лотерея | Только взвешивание + переподтверждение категории |
| Главный судья / арбитр | Layer 1 view "judging" | Текущий подход, голоса, таймер | Override результата, дисквалификация |
| Боковые судьи | Layer 4 share-link | Текущий подход, кнопки good/no lift | Только свой голос |
| Ассистенты | Layer 4 share-link | Порядок выхода, нагрузка штанги | Ничего |
| Ведущий | Layer 4 share-link | Текущий спортсмен, фото, рекорд | Ничего |
| Зал (табло) | Layer 4 broadcast view | Скоринг, текущий подход, рекорд | Ничего |
| Спортсмен / тренер | (V4) mobile companion / share link | Свой следующий вес, расписание | Заказ подхода (с подтверждением секретаря) |
| Зритель | Layer 3 public protocols | Live-протокол | Ничего |

Все эти роли читают и пишут **одно состояние турнира**, которое физически живёт в IndexedDB / save-file клиента оператора. Layer 4 (broadcast publisher) — это то, что превращает единое состояние в N представлений. Поэтому пункты "broadcast", "судейские пульты с телефонов", "табло ведущего", "table зала" из исходного списка не отдельные продукты, а **разные view одного state**.

Practical implication: до того, как делать онлайн-регистрацию, мобильные роли или Telegram, надо завершить Layer 4 (local publisher) и доказать, что архитектура держит несколько одновременных read-only/write-scoped клиентов. Это уже стоит в roadmap как V3.

## 4. Что мы делаем не так, как PowerTable

| Их выбор | Наш выбор | Почему |
|---|---|---|
| 1C / Firebird runtime | Tauri + IndexedDB + JSON save-file | Не зависим от Windows-сервера, ставится одной кнопкой |
| Stored procedures для правил | Чистые TS-сервисы + RulesPack | Тестируется юнитами, версионируется, мигрируется |
| Telegram-бот как часть продукта | Не делаем в V1–V3 | Высокая нагрузка на поддержку, низкая маржа, легко обходится share-link |
| Отдельные .lnk на рабочий стол под каждую роль | Один клиент + share-link на роль | Одна установка, нулевой ИТ-онбординг на месте |
| Online cloud sync рабочего состояния | Local-first, sync только до и после | Турнир не должен падать из-за интернета на месте |
| ISF в колонках bench/deadlift | Чистый ISF-домен | Не ломаем семантику; ISF не на грани совместимости с powerlifting-схемой |

Эти решения **не в минус** функциональности. Они в минус **технического долга**, который у PowerTable на видном месте: установка через инструкции в Telegram, ручное открытие портов, plaintext credentials, импорт через OEM CSV.

## 5. Что мы у них берём

Без сохранения операционного покрытия PowerTable / PowerGage идея "полной замены" ломается на первом реальном турнире. Берём:

- роль-разделённый workflow (см. таблицу выше);
- отчётный центр (грамоты, командные протоколы, сертификаты рекордов, разрядные карточки, абсолютка, экспорт в OpenPowerlifting/AllPowerlifting);
- ceremony-режим награждения;
- табло проектора + OBS overlay + lower thirds;
- настройка цветовой схемы турнира под федерацию;
- чёткое разделение секретарь / оператор / помощник;
- лотерея взвешивания;
- duplicate-resolution import заявок;
- расчёт расписания потоков по длительности;
- разрядные нормативы и кандидаты с ручным подтверждением;
- архив рекордов между турнирами;
- сценарий восстановления турнира после потери устройства.

Эти возможности уже стоят в `current-implementation-plan.md` §4 в фазах V1.x → V3. Этот memo не добавляет новых фаз, а фиксирует **зачем** они там стоят.

## 6. Что меняется в V1.x до UAT

Ничего из roadmap не двигается, но V1.x backlog (§4 в `current-implementation-plan.md`) расширяется двумя пунктами, которые нельзя честно проверить на real-meet UAT без них:

1. **Tournament readiness checklist.** Перед стартом дня оператор должен видеть pre-flight: категории определены, дисциплина выбрана, плиты заведены, судьи назначены, потоки сформированы, заявки закрыты, взвешивание проведено, базовые рекорды импортированы, save-file подписан и зарезервирован. Без этого экрана UAT с реальной федерацией провалится по человеческой ошибке, а не по ПО.
2. **Минимальный набор отчётов для UAT.** В `report-registry.ts` уже есть `official-protocol`, `athlete-cards`, `blank-sheet`, `diplomas`, `awards-ceremony` (planned), `classic-csv`, `multirep-csv`, `openpowerlifting-export`. Для реального ISF-турнира этого не хватает: отсутствуют **командный протокол** (хотя team scoring уже считается), **сертификаты рекордов**, **порядок взвешивания** и **итог по медальному зачёту**. Эти четыре пункта добавляются в V1.x как дополнения к существующему registry — без архитектурной перестройки в полноценный V2 report registry.

Полный V2 report registry с фильтрами, языками и федерационными шаблонами остаётся за V2.

## 7. Что НЕ меняется

- V2 (billing, RulesPack, sync, athlete↔nomination split) остаётся следующей крупной фазой.
- V3 (multi-federation, local broadcast publisher, share-link роли) остаётся.
- V4 (WC, governance) и V5 (federated records, mobile companion) остаются.
- Out-of-scope из §11 architecture-v1 не меняется: powerlifting-меты, armlifting/strongman, athlete portal, full federation CRM — мимо.

## 8. Один абзац для команды

Streetlifting OS заменяет PowerTable и PowerGage не тем, что копирует их фичи, а тем, что воспроизводит **роль-разделённый workflow** на чистой offline-first архитектуре без 1C, Firebird и Telegram-бота как зависимостей. Полная замена достигается через V1.x (надёжный оператор-клиент + минимум отчётов для real-meet UAT) → V2 (billing, sync, RulesPack) → V3 (multi-federation + local broadcast publisher с N ролевых view) → V4 (WC + governance) → V5 (federated records). До реального UAT сначала закрываем checklist готовности и недостающие отчёты, чтобы не строить V2 на ложных предположениях V1.
